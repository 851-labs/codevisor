# Screen sharing

The engine behind the Screen Sharing pane, in these targets under `packages/swift/ScreenSharing` (the bench's `ScreenSharingBenchScenes` and `CodevisorBench` live under `apps/screen-sharing-bench`, see its README):

| Target | Links | Holds |
| --- | --- | --- |

| `ScreenSharingTesting` | `ScreenSharing`, `ScreenSharingBench` | The in-process RFB server the suites drive and the replay of recorded RFB fixtures. Never a dependency of a product target. |
| `ScreenSharingV2` | `ScreenSharing`, CodevisorClient, CodevisorNet | Engine v2 (see [Engine v2](#engine-v2)): `Profile/`, `Encode/` (the `ScreenSharingTileEncoder` interface and its VCP and VideoToolbox implementations), `Transport/` (the media transport seam and its `codevisor-media` adapter, the in-band frame metadata), `Host/`, `Viewer/` (decode, recovery gate), `Present/` (the display-link compositor), `Session/` (the product's control plane on QUIC streams, the v2 viewing session, the host link, and the media endpoint and connector both viewers use). Folders are layers; targets are dependency edges. Codevisor screen sharing has no WebRTC: engine v2 replaced it on every surface, and 851-3826 deleted the `ScreenSharingWebRTC` target and the WebRTC binary. `Viewer/`, `HostInput/` and `VNC/` are macOS-only (`#if os(macOS)`); the rest compiles for iOS. Product feature code (the Composable Architecture reducer, the backends and runners, the host service) stays in `CodevisorCoreMac/ScreenSharing`.

## Native Screen Sharing

A native media library and a native macOS workspace pane with authenticated signaling and explicit remote control. No HTTP plugin server or webview participates in video delivery.

The working path is engine v2 (see [Engine v2](#engine-v2)): ScreenCaptureKit → dirty tiles → VCP (or VideoToolbox) HEVC per tile → `codevisor-media` over iroh QUIC → VideoToolbox decode → CVPixelBuffer-backed Metal textures. Linux machines are viewed over VNC instead (`VNC/`, `RFB/`).

**Capture colour.** Standard dynamic range capture asks ScreenCaptureKit for sRGB. Its `420v` frames hold sRGB-encoded values (and carry an sRGB `CGColorSpace`) but are tagged with the BT.709 transfer function, and a VideoToolbox session tagged sRGB (both engines' encoders) converts a frame whose tags differ from its own, which brightened every colour (T8 run 41501773369: host (89,25,128) arrived as (101,28,136); after the fix, run 41537407738, as (91,27,127)). Capture therefore retags a `420v` frame whose colour space is sRGB with the sRGB transfer before it reaches a sink. BGRA frames carry an sRGB `CGColorSpace` and need no retag, and high dynamic range capture is never `420v`.

## Native workspace pane

Run `bun run dev:macos`. In a workspace hosted by a Mac, open New Tab → Screen Sharing and select a display from the searchable chooser to connect. The host must run this version of the native app and allow Screen Recording. The native toolbar shows the machine name and resolution, View/Control, clipboard and connection details. The video always scales to fit the pane. Closing the tab ends the session.

The viewer sends a v2 start (its media endpoint address, no SDP) through the existing machine-authenticated, relay-aware client to `POST /v1/screen-sharing`. The server validates the active workspace and native pane, then forwards the request over Codevisor’s authenticated Unix bridge to the app’s native host service, which answers with its own media address and a session token. Signaling stays transient; only the stable display UUID and fit preference enter pane metadata. Synced size preferences update the existing native surface; a display change from another client requires a fresh Connect. Websites are rejected even on loopback.

One viewer owns the host at a time. Capture begins after its media connection is accepted. The host shows a menu-bar Sharing indicator with Stop Sharing. An eight-second heartbeat renews a 25-second lease; loss of the viewer stops capture. Sleep, session deactivation, display changes and SCK errors also stop it. A connection without video ends after three heartbeat intervals, and decoder failures end viewing on the next heartbeat. Hiding the viewer (switching tabs) keeps the connection for five minutes, like Apple Screen Sharing's window: control is given back at once, and returning shows the live picture and asks for control again without renegotiating. Closing the viewer, or hiding it for longer, tears down media; returning then renegotiates. A start from the same pane replaces that pane's earlier session if its stop hasn't reached the host yet, rather than finding the host busy. A newer negotiation waits for the old stop request, and generation checks reject late frames and signaling responses. Reopening the app requires an explicit Connect.

The host captures the display natively up to 3840×2160 (`ScreenSharingV2Profile`). When the viewer asks for a size on `codevisor.display.v1`, the host mirrors the display onto a HiDPI virtual display of that size (at most 1920×1080 points) and captures that instead; restoring returns to the physical display. Media goes direct when the two endpoints can reach each other, otherwise through the cloud relay; the cloud channel still carries signaling.

## Native control

New panes start in **Control** mode and request control when video and the control channel are ready. The selector stays interactive while connecting; choosing **View** cancels that pending request. The selected mode survives menu interactions and reconnection. The host also needs Accessibility permission (called Device Control and Data Access in macOS 27). Control doesn't take the keyboard: input goes to the host once the video is clicked, so arriving at the pane by keyboard (⌘[ through the sidebar, a tab switch) leaves the app's shortcuts working. **Control–Option–Escape** hands the keyboard back to the app and stays in Control; choosing **View** gives control back. Clicking outside the video or losing keyboard/window focus suspends input forwarding and releases held input without changing the selected mode. Hiding the pane gives the control lease back (it is requested again when the pane is shown); closing it, disconnecting, and the host’s Stop Sharing action tear down the connection and its control lease. A denial, revocation or input failure keeps **Control** selected and shows why, with Request Control to try again; only the user’s own release (choosing View) switches to **View**. The host indicator changes to “Controlled” while a control lease is active.

A fresh host-issued control lease binds input to the current authenticated v2 session and selected display. One-second heartbeats renew a separate three-second control deadline, checked every 250 ms. Expiry, permission loss, malformed messages and channel closure revoke the lease and release tracked keys/buttons. Delayed grants are released after viewer cancellation; input from an expired lease cannot revive control. No control lease, input or key content enters pane metadata or logs.

The control stream (an ordered QUIC stream on the media connection) carries key/button transitions, scroll deltas and motion. A 16 ms viewer tick coalesces waiting motion; transitions flush it first to preserve ordering. Each button event contains its own normalized coordinates. The send queue admits at most 16 KiB, and the receive queue at most 256 messages / 64 KiB; congestion or invalid input closes control instead of accumulating actions. This first implementation deliberately uses one reliable ordered channel. A separate unreliable motion channel needs button-generation coordination before it can replace this ordering contract.

The native surface maps through fit-to-pane letterboxing and backing-pixel scale. The host maps normalized coordinates into Quartz display bounds, including negative origins. It uses public CGEvents from a private event source, with no automation delays or app activation. Tagged injected events are excluded from capture by a viewer on the same Mac. Fractional trackpad deltas accumulate before conversion to integer pixels.

Physical Mac key codes use the host’s keyboard layout and input method. With viewer Accessibility permission, a focused video surface in Control mode forwards system shortcuts such as Command-Space and Command-Q. Without it, control still works and those shortcuts stay on the viewing Mac; a Mac host's pane says so, naming that Mac and the app to allow. A Linux desktop needs no permission. Physical typing, modifiers, repeat, mouse buttons, dragging and scrolling are forwarded; there is no dedicated Unicode composition UI. The clipboard is shared automatically, with explicit transfer as the alternative (below). The protocol also has a bounded, separate text-insertion message.

## Clipboard, cursor, audio and connection details

Whatever can be copied and pasted on a Mac (images, rich text, HTML, app-specific formats, several items at once) moves between clipboards, up to 32 MB, in one of two ways, chosen per machine from the clipboard menu. **Use Shared Clipboard** (the default) works like Apple Screen Sharing's: while the viewer controls the host, a copy on either Mac reaches the other however it was made (keys, Edit menu, context menu). Each side checks its pasteboard's change count every 250 ms, which never reads the contents, and reads the contents only after a copy: every type each item itself provides, not the conversions the pasteboard server synthesizes (a screenshot sends its PNG, not a TIFF copy too). The host sends its copies once the viewer asks on `codevisor.clipboard-sharing.v1`, and only those made after it asked. The viewer sends a copy made elsewhere when the video has keyboard focus in a key window, so a paste on the host already has it. A copy a side wrote for the other never bounces back; when both copy at once the viewer's copy wins. Items marked concealed, transient or auto-generated (nspasteboard.org, as password managers do) are never shared. A host that predates the channel still receives the viewer's copies but doesn't send its own; turn sharing off for **Send Clipboard** and **Get Clipboard** there. With sharing off, those menu items move the clipboard one way on request.

Either way, a separate ordered stream carries the transfer; it cannot fill the keyboard/mouse channel. The viewer announces rich content in its `codevisor.clipboard-sharing.v1` message (an optional field older hosts ignore), and a host that understands it answers. Until both sides know, and always with a host, viewer or VNC server that predates it, only plain text (64 KiB of UTF-8) moves, in 2 KiB chunks with stop-and-wait acknowledgments, byte-for-byte the format older peers decode. Rich content is the items' types and data in a binary property list, sent in 48 KiB chunks with up to eight unacknowledged. A transfer that makes no progress for ten seconds expires. Invalid or incomplete data is rejected, and partial data is discarded on cancellation. A download cannot replace a newer local copy made while it was in flight. File URLs and file promises stay on the Mac that copied them (there is no file transfer), and nothing reaches signaling, logs or the workspace database.

A Linux desktop that `codevisor-server` set up (`desktop: "xfce"` in `screen-sharing.json`) gets the same rich clipboard without VNC's text-only cut text. The server announces it with a `clipboard-host` text frame on the VNC WebSocket, next to the control lease, and then carries the same transfer messages there; the Mac stops sharing RFB cut text and relays its clipboard channel through those frames. The server reads and writes the X clipboard with `xclip` (PNG, JPEG, GIF, HTML, RTF and UTF-8 text) and learns of copies from XFixes selection events through a small `python3` ctypes helper, so it never polls. X lets one `xclip` serve only one type, so a paste on the desktop gets the best single type the Mac copied: an image if there is one, otherwise text, then HTML, then RTF. A Mac item with only TIFF is sent as PNG. Without `xclip`, `python3` or XFixes the server doesn't announce, and the desktop keeps VNC's plain-text clipboard.

ScreenCaptureKit includes the host cursor in video until the viewer subscribes on `codevisor.cursor.v1`. The host then stops capturing the cursor and publishes its position about 120 times a second, with its shape and scale, and the viewer draws it as an overlay. If the channel closes, the cursor returns to the video. AppKit cursor rectangles suppress the viewer cursor only inside the active control surface and restore the local arrow on release/exit.

System audio is captured by ScreenCaptureKit (excluding Codevisor's own) only while the viewer subscribes on the audio channel. The host encodes it as 48 kHz stereo Opus; the viewer buffers and plays it.

Connection Details shows the engine, the direct/relay route, decoded resolution, interval presentation rate, receive bitrate, round-trip time, decode p95 and recovery counters. It omits addresses and tokens. Statistics run separately from the control heartbeat.

## Connectivity and recovery

Media rides the app's iroh endpoint (see [Product integration](#product-integration-e8-851-3823-mac-to-macs-engine-since-851-4064)): direct when Local Network access and the network allow it, otherwise through the cloud relay. No STUN, TURN or other third-party server is involved. A network switch migrates the QUIC connection rather than renegotiating.

After an established connection drops, the viewer releases input and reconnects with `restart` (the Mac at most three times, iOS twelve times with a backoff). The host accepts a replacement only for the same still-live viewer lease and display; host stop, sleep, display change, cancellation and lease expiry prevent it. The replacement is a fresh v2 session, and control must be requested again, so no queued input or decoder state crosses connections. Recovery inside a session (lost tiles, keyframes, the frame acknowledgements that drive the host's rate) is engine v2's own; see [Engine v2](#engine-v2).

## Ownership and limits

- Capture callbacks feed the engine on the capture queue, without per-frame main-actor tasks. SCK uses a queue depth of three.
- Hardware acceleration is required at VideoToolbox session creation. Software fallback is disabled.
- Rendering has a one-frame mailbox, one command buffer in flight, and one retained last frame for resize redraw. Slow consumers replace stale waiting frames. CVPixelBuffers and their Metal textures survive until the GPU completes its reads.
- The host link and capture owner must call `close()` / `stop()`. The native viewer backend implements reconnect, the heartbeat watchdog and hidden-pane teardown.
- `ScreenSharing` holds frames, the mailbox, metrics, the input/control/clipboard messages, the clipboard transfer, the `ScreenSharingMessageChannel` contract (a QUIC stream in v2, an in-memory pair in tests), the `ScreenSharingViewingSession` contract a viewer renders from, and by stage folder `Capture/` (ScreenCaptureKit) and `Render/` (the Metal renderer, which draws biplanar YCbCr and packed BGRA frames, tiled or whole). `ScreenSharingV2ViewingSession` and `VNCScreenSharingSession` (`VNC/`, over the `RFB/` protocol) are the two viewing sessions. The viewer feature in `CodevisorCoreMac` is a Composable Architecture reducer over a `ScreenSharingViewerBackend` (the native backend owns signaling) with the control lease as a child reducer over a `ScreenSharingEndpointClient`; input events stay on the data plane inside the endpoint.

Run the suites with `bun run swift:test`; `bun run check` runs them with the rest of the repository's checks.

## Engine v2

`ScreenSharingV2` is the tiled engine of the [HP-class engine design](https://linear.app/851/document/hp-class-engine-design-0b6e749493a3) (E3, 851-3817; tiles E5, 851-3820): ScreenCaptureKit → dirty tiles → admission → `ScreenSharingTileEncoder` → `codevisor-media` over iroh QUIC datagrams, one stream per tile → VideoToolbox decode per tile → one composed picture → presentation. There is no jitter buffer and no queue deeper than one frame. The bench drives it with `share` and `view --source codevisor` (engine v2 is the bench's only engine since 851-3826); the product uses it Mac to Mac (E8, 851-4064).

**Profile** (`ScreenSharingV2Profile`, from the [encoder lab](https://linear.app/851/document/encoder-lab-851-3767-5f6ac641b750)'s public configuration):

- Capture is native up to 3840×2160 px and scaled to fit 3840×2160 above that, at 60 fps, in `420v`.
- Four horizontal tiles above 1440 rows, as Apple's High Performance mode uses (`ScreenSharingV2TileLayout`): each is the full width and a quarter of the height rounded up to 16 rows, the last one taking the rest (3840×544, three times, then 3840×528 at R1x2). Each tile is its own VideoToolbox session and its own `codevisor-media` stream (the stream number is the tile index). An encoder may report its own tile height, which travels in the frame metadata. At 1440 rows and below a capture is one tile: on tamale (encoder lab run 41546464722) four 1080p tiles took 10.2 ms and 6.6 Mbit/s to scroll against 6.7 ms and 1.8 Mbit/s for one, and only won on small changes (typing 3.4 against 8.6 ms), while one 4K frame took 81 ms against 15 ms for four tiles.
- Four refinement passes, two frame intervals apart (`refinementPasses`, `refinementGapFrames`): low-latency rate control spends few bits on a frame that just changed, so a tile that stops changing is encoded again from the same capture until it has had four passes, building it towards lossless.
- HEVC Main with low-latency rate control (it writes 4:2:0 even when asked for 4:4:4), real time, no frame reordering, `MaxKeyFrameInterval` 0 (no periodic keyframe) and `EnableLTR`.
- `AverageBitRate` follows the transport's encoder ceiling (0.85 × its capacity estimate / (1 + the FEC ratio)), checked every 250 ms and changed only when it moves by more than 10%, between 200 kbit/s and 45 Mbit/s (a 1 Mbit/s floor was the whole of N7's link; 851-3822), shared between the tiles of each update: before an update, each of its tiles' sessions is set to the total divided by the number of tiles in it (when that moves its rate by more than 10%). A one-tile change or refinement pass gets the whole budget, and a full-screen change gets a quarter per tile, so the tiles together never aim above the total. Splitting it evenly all the time held each pass of a refining tile to a quarter: in the encoder lab (4K, 4 tiles, 4 refinement passes) the whole budget per tile lifted test-cards PSNR-Y from 51.8 to 54.1 dB and typing from 69.4 to 75.5 dB; giving every session the whole budget all the time let Tier 2 video reach 77.6 Mbit/s (run 41580100928).

**Host** (`ScreenSharingV2Host`, a `ScreenSharingFrameSink`). A capture goes into a one-frame slot; a newer one replaces it, and the slot keeps the union of the dirty tiles of every capture it held. A capture's dirty tiles are those its ScreenCaptureKit dirty rects (`SCStreamFrameInfo.dirtyRects`, in the captured buffer's pixels at native scale) touch; a capture scaled to fit has its rects dropped, since they are not in its buffer's pixels; a frame without dirty rects (the synthetic Tier 1 source) dirties every tile, and the first capture encodes every tile. A reported tile is then compared with the previous capture's pixels, row by row until the first difference (`tilesUnchangedByPixels`): ScreenCaptureKit reports what the window server redrew, and an app that redraws its whole window on each change (the bench player does) would otherwise dirty every tile. In Tier 2 typing (run 41559577380), before the comparison, 1,026 captures encoded 3,926 tiles. Each encode is an *update*: a numbered set of tiles from one capture, submitted to their sessions concurrently so they run in parallel (`updateSubmit` and `encodeCall` in host metrics time the submission); a session keeps only the update's identity and timestamps, never the capture's pixels, so ScreenCaptureKit gets its buffers back as soon as the tiles are cut. Clean tiles are skipped. A tile is busy from submit until its output arrives. A change may start while each of its tiles has at most one encode in flight, so the hardware starts the next capture's top tile while the last capture's bottom tile is still encoding; at R1x2 scroll, waiting for every tile first held v2 to 29 updates a second (Tier 2 run 41560829092, against 54 for Apple HP). A refinement needs its tile idle. An encoder answers a tile it had nothing new for (a refinement of a picture it has converged on) with `.unchanged` and the update's id, which ends that tile's refinement without a retry unless the tile has changed since. An update also starts only when the transport admits (its send backlog fits one frame interval at the estimate); otherwise it waits, and admission is asked again after every ack and once the backlog should have drained at the estimate (1–8 ms). With nothing new to send, the tiles whose refinement passes are due become a refinement update, encoded from the last capture. Each encoded tile is sent at once from VideoToolbox's callback, which only borrows its bytes. The host keeps the last encoded capture so it can answer a loss or refine a tile when the screen is idle. An update's tiles are cut from the capture together, each into a pooled buffer of the same pixel format with the capture's colour attachments (`tileCut` in host metrics), with one Metal command buffer of blits (a CPU copy only when Metal can't map the buffer): copying the four tiles of a 4K `420v` frame on the CPU took 0.34 ms, 2% of a core at 60 updates a second. A tile the encoder fails is encoded again one frame interval later, or with the next capture.

**Recovery** (E6, 851-3821) is per tile and by reference, never a periodic keyframe. The encoder marks long-term references (`RequireLTRAcknowledgementToken`); the token rides in the frame, the viewer acknowledges it after decoding it, and the host passes acknowledged tokens with that tile's next encode (`AcknowledgedLTRTokens`). Only tokens a tile sent since its latest keyframe count. Every loss makes the next encode of that tile a refresh, encoded from the last capture when nothing newer is waiting: `ForceLTRRefresh` (a P-frame from a reference the viewer acknowledged) once the tile has an acknowledged reference, and a keyframe of that tile alone before that, or when the viewer asks for one (`ScreenSharingV2Recovery`). A refresh lost on the way is answered with another refresh, not a keyframe: losing it says nothing about the reference it predicts from, and a refresh that arrives but doesn't decode makes the viewer ask for a keyframe. The design's rule (a keyframe after two lost refreshes) was the likely source of keyframes in loss bursts: in Tier 1 run 41624415883 (scroll N3) one rep sent 5 keyframes for 10 lost frames with no decode errors and no viewer requests, and a keyframe drains slowly at a low estimate and loses more frames (VideoToolbox may also answer `ForceLTRRefresh` with a keyframe; the bench doesn't separate the two yet). The host learns of a loss three ways: the transport gave up on a frame (`FrameLost`), a send failed (a keyframe if the failed frame was one), or the viewer asked (`RefreshRequested`). A frame VideoToolbox drops or fails is encoded again from the last capture if nothing newer comes, with its refresh if it carried one, and an encoder session VideoToolbox invalidates is reopened on the next encode, which starts with a keyframe. On the viewer, `ScreenSharingV2RecoveryGate` decodes a tile only from its first keyframe on. After a skipped frame it drops that tile's frames until a keyframe or a refresh; the transport has already told the host. A frame that fails to decode asks the host for a refresh, and a refresh or keyframe that fails to decode, or a lost decoder session, asks for a keyframe and waits for one. `codevisor-media` repeats a request until a recovery frame arrives (at most 50 times). The gate starts a new epoch with every keyframe or refresh it admits, so a failure reported for a frame submitted before the latest recovery frame doesn't break the tile again. A decoder session lost asynchronously is replaced before the next keyframe, and a keyframe that finds its session dead is decoded once more on a new one. **Stall detection:** a tile that broke without asking (the transport gave up a frame and told the host), or that never got its first keyframe, asks once when a frame is rejected 100 ms or more after it broke (`ScreenSharingV2RecoveryGate.stallNs`, counted as `stalledTiles`), for a keyframe if that's what it waits for; the transport repeats that request. Waiting for a stream's first keyframe isn't timed as a recovery. Viewer metrics count `refreshRequests`, `keyframeRequests`, `staleDecodeErrors` and `recoveredTiles`, and time each tile from break to its next decoded frame (`tileRecovery`); host metrics count `requestedRefreshes`, `requestedKeyframes` and `lostFrames`. Every 250 ms, with an encode, the host passes the transport's loss rate, round trip and estimate to the encoder (`observeNetwork`, a no-op for VideoToolbox).

**Access units** are HEVC length-prefixed NAL units, as VideoToolbox writes them, with the VPS, SPS and PPS prepended to keyframes. Delta frames go to `send_frame` without a copy.

**In-band metadata.** Each frame's metadata (46 bytes, big endian) is a version byte (2), a flags byte (1 = refresh or keyframe, 2 = refinement), the update number (4 bytes), the update's tile mask (bit *n* = tile *n*), the tile count, and the picture's width and height and the tile height (2 bytes each), the source timestamp (the ScreenCaptureKit display time, mach absolute ns, also the content identity), the host's clock identity, and four microsecond durations: `capture` (display time → capture callback), `admission` (callback → encode submit), `encode` (submit → VideoToolbox output) and `handOff` (output → `send_frame`). The viewer records them in the [frame timeline](#frame-timeline) as `capture`, `hostQueue`, `encode` and `handOff`, with the frame's `assemble`; `network` is half the QUIC round trip, polled once a second, and `jitterBuffer` is 0. Host metrics add `send` and `sendQueue` per acked frame and the viewer's add `assemble` (first packet → frame complete) and `recovered.*` counters.

**Composition.** The viewer keeps one decoder per stream and the latest decoded image of each tile. It groups tiles by update, holds each update's decoded images with the update until it is released, and presents an update only when each of its tiles has been decoded or given up (rejected while awaiting recovery, a decode error, or a skipped frame on that stream); a newer frame on a stream also gives up an older update's tile that never arrived, and at most 8 updates wait. Updates are presented in order, so the tiles of one capture always appear together and a scroll never shows two captures at once. A ready update is composed by copying every tile's latest image into a pooled full-size buffer in the newest tile's pixel format with a Metal blit, or on the CPU when Metal can't map a buffer (`compose` in viewer metrics), so the renderer draws one picture and scaling never shows a seam between tiles; with one tile the decoded image is passed on as it is. A tile that decodes after its update was given up is composed and presented at once (`lateTiles`). With `presentsTiles` (`ScreenSharingV2ViewingSession.presentsTiles`, which the Mac pane's `ScreenSharingViewerBackend` sets before `start`; the bench's `view --tiles on|off`, on by default; Simulator streams keep composed pictures, because `SimulatorScreenFeed` reads the whole picture's pixels; 851-3976), nothing is composed once every tile has an image: the viewer hands the renderer a tiled `ScreenSharingVideoFrame` (`tiles`, each a decoded image and its rows of the picture, and `size`, the layout's whole picture, which is what `onFrameSize` reports; its `pixelBuffer` is the top tile, so anything that reads pixels has to read `tiles`). Updates are still shown whole: Apple HP shows its tiles together too (Tier 2 run 41982904710: its bottom tile was as old as its top one, and no frame was torn). `ScreenSharingMetalEncoder` draws each tile with the whole picture's aspect-fit viewport and a scissor rect at the tile's rows rounded to whole pixels, so adjacent tiles share an edge with no gap or overlap. The fragment shader (`tileSample`, with the tile's rows in a `ScreenTile` at fragment buffer 1) samples the tile in texel units: the picture's interpolated coordinate times the picture's rows, minus the tile's first row, so a tile reads the same positions the composed picture would. A decoded buffer taller or wider than its share shows only its own rows and columns. On the rows where the filter would reach across a tile edge, the shader also reads the neighbouring tile's edge row (bound at textures 2–3 above and 4–5 below; the BGRA variants use 2 and 4) and blends the two itself. Without that, each tile clamped its filter at its own edge, which left seams of up to 66 levels on text and 125 on noise at 1.5×, 1/1.5× and a 1373×772 window (851-3976, evidence on #1022). With it, a 4K picture with v2's 544-row tiles is within 1 level of the composed one at every scale on text and within 2 on noise, in 4:4:4 full range and 4:2:0 video range (`atEveryScaleATiledPictureIsWithinTwoLevelsOfTheComposedOneEvenAtTheTileEdges`). The plane's scale to the picture comes from its width (half for 4:2:0 chroma), so a tile of odd height doesn't shift its chroma. Untiled frames sample as before. Decoding each stream on its own queue didn't help (851-3976, Tier 2 run 41956852379 at R1x2 window-drag and scroll): VCP's tiles share one hardware encoder, so they arrive about 2.5 ms apart (the slowest tile took 8.5 ms to encode against 6.0 ms per tile), and an update waits for its last tile whichever queue decodes it, so its first tile still reached the screen 9.7–10 ms after it arrived. The frame timeline gets one record per update, from the tile that finished last on the host; refinement updates are presented without a source timestamp, so they don't count as new content.

**Present.** The bench presents on arrival by default: decoded frames go to the same `ScreenSharingVideoSurface` as v1, which draws into the next drawable at once (`view --present arrival`). `ScreenSharingV2DisplayLinkView` (macOS, `--present display-link`) instead draws the newest decoded frame on each `CAMetalDisplayLink` update (`preferredFrameLatency` 1) on its own thread, through the same Metal encoder, and redraws the last frame after a resize. That was the design's §3.4 comparison: on Tier 2 at R1x2 typing, arrival was one refresh faster (47.3 against 63.8 ms p50 image age, runs 41245803066 and 41244008157), because a decoded frame waited 13 ms for the display link's update and presented a refresh later.

Tests drive the host and viewer over an in-memory `ScreenSharingMediaTransport` pair (including a dropped frame repaired by an LTR refresh and a four-tile picture composed from the hardware encoder's tiles) and over a real iroh connection on loopback. The host takes its clock and timers from a scheduler, so tests step refinement and admission retries by hand.

Tests that open real hardware encoders sit under the serialized `HardwareCodecTests` suite with the `hardwareCodecLock` trait (CodevisorTestSupport): one such test runs at a time across every test process on the Mac, a test waits at most 45 seconds for the lock (blocking in `flock`, so a release wakes it, and under the tests' 1-minute `timeLimit`) and then skips, naming the process that last held it, and every later one in that process skips at once. A test that can't open the lock file fails. Each waits for frames with `cancellableWait`, so its 1-minute `timeLimit` ends it. The VCP tests also call `HardwareEncoderBudget.require` first: a test may hold at most 6 low-latency HEVC sessions (`maximumSessionsPerTest`) (a VCP tile counts as 2), and it skips, saying how many it got, when a probe can't open and encode on that many (some Macs have only 4–5 in total, 851-4007). The probe runs on its own thread with a 10-second limit, so an encoder call that never returns skips the test too. The VCP refinement test runs every pass (`.standard` policy), since VCP's own policy ends refinement at the first pass under 200 bytes, and it steps the scheduler a refinement gap plus a refresh, since the host aligns refinement wakes to the display's refresh phase. `swift:test` stops a test bundle that runs past 10 minutes, so even an encoder call that never returns can't hang the pre-commit hook.

### VCP encoder (E3b, 851-3819, v2's default since 851-4048)

`ScreenSharingVCPTileEncoder` (`Encode/VideoProcessing/`) is a `ScreenSharingTileEncoder` over VideoProcessing's private `VCPCompressionSession`, the real-time encoder Apple's High Performance mode uses ([teardown](https://linear.app/851/document/apple-hp-teardown-851-3766-c9b9227a0381)). It is loaded with `dlopen` inside our own process and needs nothing from macOS Screen Sharing. It is engine v2's default encoder (851-4048: in 851-3975's Tier 2 runs it beat Apple HP on every T8 text metric and encoded scroll and window-drag tiles in 8.7 ms against VideoToolbox's 14.3, a refresh sooner, within M3's CPU and bitrate limits). `CODEVISOR_SCREEN_SHARING_V2_ENCODER` (`ScreenSharingV2EncoderKind.configured()`, default `vcp`; the bench's default for `--encoder`, and what E8 reads) set to `vt` selects VideoToolbox instead. `ScreenSharingV2Encoders.make` builds it after `ScreenSharingVCPSelfTest` passes, behind `ScreenSharingFallbackTileEncoder`; when VCP can't load, fails its self-test or fails mid-share, the share runs on VideoToolbox (`encoderFallbacks`, `encoderFallbackReason`). The bench fails rather than measure VideoToolbox when `--encoder vcp` is unavailable. 851-4009 reported that VCP sessions held the hardware encoders after they stopped on an M4 Max; it didn't reproduce on an M1 Pro or the minis' M6 (`CodevisorBench encoder-release`: every slot comes back on `stop()`), so it was closed; reopen it with that command's output if it shows up again.

- **Sessions.** One 1-tile session per layout tile (the same tiles as the VideoToolbox encoder: a quarter of the height rounded up to 16 rows above 1440 rows, one tile below), with `Usage` 42 and `RealTime` in the encoder specification and Main 4:4:4 because the source attributes are `444f`. Capture stays BGRA (`sourcePixelFormat`); a Metal compute kernel (compiled once per process) converts each of the update's tiles straight from the capture into its own pooled `444f` buffer (BT.709, full range), every tile in one command buffer (`vcpConvert`), and a refinement of the same capture reuses those buffers (keyed by its source timestamp). A capture of another size, during a display change, is scaled whole into `444f` by a `VTPixelTransferSession` and then cut into tiles with `ScreenSharingV2TileCutter` (`tileCut`). Converting the whole frame and then cutting it, as every capture did before 851-3976, cost window-drag 5.9 ms of `updateSubmit` at p50, against 3.9 ms per tile (Tier 2 runs 41951480826, then 41956852379 and 41959771811), and host CPU went from 44.1% to 41.4–41.9%. Image age didn't change: the earlier commit still misses the same compositor cutoff. A `VTPixelTransferSession` did the conversion before: it is exact on an M1 Pro but turned white into 254 on the minis' M6 (Tier 2 run 41678463486), which capped test cards at 48 dB; the encode lab hid it because its reference came from the same conversion. The kernel costs 0.4 ms of CPU and 1.7 ms of wall time for a 4K frame, against 0.23 ms and 3.2 ms (M1 Pro). The converted buffer is tagged BT.709 primaries, sRGB transfer and BT.709 matrix, what the session declares: left with only a matrix tag, the minis' M6 shifted mid-greys down by up to a level (grey 40 arrived as 39 in Tier 2 run 41695143473, with black and white exact), the transfer conversion E5 found for VideoToolbox's `420v` (#991); an M1 Pro passes the levels through either way. `MaxAllowedFrameQP` is 28 (left alone, a 1-tile session codes changes at about QP 45 and four refinement passes don't bring text back: Tier 2 run 41611186948 had test cards at 33.3 dB `psnr_y` and 24 dB on the text, against 46 dB and 44.6 dB for VideoToolbox; capped at 28, Tier 2 run 41621890275 measured 40.5 dB and 35.1 dB on the text, with `psnr_cbcr` 50.8 dB and ΔE00 1.6 against Apple HP's 50.4 dB and 1.1, and video stayed at 51 Mbit/s), `ExpectedFrameRate` is the capture rate, `MaxKeyFrameInterval` 0, and each tile gets a quarter of `setBitrate` as `AverageBitRate` (at most 60 Mbit/s in all) and of a `[bytes, 0.05 s]` `DataRateLimits` that follows it from the v2 floor (200 kbit/s) up to Apple's 60 Mbit/s ladder top. A floor at the ladder's 20.8 Mbit/s kept VCP above every link under about 25 Mbit/s. Encode lab run 41730525816 (tamale, 4K, 4 tiles, LTR on) found that a lower window doesn't starve keyframes: with a 1 Mbit/s target and window, the first frame (478–534 KB) and the LTR refresh still came out, with nothing late or dropped. Scroll fell from 16.9 to 9.2 Mbit/s and video from 20.9 to 4.4 Mbit/s against the 20.8 floor (PSNR-Y 44.5 → 32.2 dB on scroll). VCP goes no lower than that, and its LTR refresh stays 0.76–1.5 MB at any rate, against 6–31 KB for VideoToolbox's low-latency sessions, which track a 5 Mbit/s target exactly. `DataRateLimits` changed neither VideoToolbox's frame sizes nor its encode times there, so the VideoToolbox sessions don't set one. Only the update's tiles are encoded: each is submitted in turn (the call returns at once) and the hardware encodes them in parallel.
- **Why not one session with `NumberOfTiles` 4**, as Apple's agent opens it: its tiles are one stream with a shared reference buffer, made for Apple's viewer, which decodes every tile through one decoder in tile order. Through one decoder per tile only 4 of 80 tile pictures decoded (64 of 80 with `ExpectedFrameRate` 240); through one decoder all 80 did (local probe), and Tier 2 run 41578531880 showed only keyframes decoding. Per-tile streams, decoders and loss recovery need independent sessions. Raising `ExpectedFrameRate` to Apple's 240 also cost bits: tiles stopped converging and scroll took 13.3 Mbit/s against HP's 8.4 (run 41573286082).
- **Frames.** A changed tile is coded at about QP 45 and sharpens only when the same capture is encoded again, which is what the host's refinement passes do. A refinement pass is capped at QP 6 (`highestRefinementQP`) while `setBitrate` is at least the bottom of Apple's ladder (20.8 Mbit/s; below it, on a constrained link, refinements keep 28, because VCP honours the QP cap through `DataRateLimits` and a 4K text tile refines in a burst of about 0.5–0.7 MB), and the next change goes back to 28, so a still converges to near lossless while motion keeps its bits (851-3975). In encode-lab run 41650908075 (tamale, 4K, 4 per-tile sessions, 4 passes), the settled test-card PSNR-Y went from 46.0 to 62.4 dB and PSNR-CbCr from 67.4 to 78.5 dB. VideoToolbox 4:2:0 reached 55.5 / 62.4 there. Test cards cost 7.0 Mbit/s instead of 2.2. Scroll and window-drag didn't change (9.6 and 7.2 Mbit/s), because refinement waits until a tile stops changing. Idle-cursor fell from 0.13 to 0.04 Mbit/s. Caps of 16, 10 and 2 gave 54.8, 58.9 and 66.3 dB for 3.9, 5.5 and 9.4 Mbit/s; two passes did as well as four. VCP honours the cap through the 50 ms `DataRateLimits`. VideoToolbox's low-latency rate control drops frames when its cap changes mid-stream, so its sessions keep no refinement cap. A session answers a frame it skips (a converged or unchanged picture, or a drop) with a callback with no sample; presentation times are kept at least 1/240 s apart. A skip of the capture the session last encoded is `.unchanged` for that update (the host frees the tile and ends its refinement); a skip of any other capture is a drop and is encoded again (the host already leaves out tiles whose pixels didn't change, so VCP doesn't refuse those forever); a skipped refresh is a drop that keeps its refresh. A session's encode and its close are serialized, so stopping never races a submit. A tile whose encode VCP refuses is a `.failed` output, so the fallback takes over without re-encoding tiles VCP already accepted. An output whose size isn't the tile's is a failure. The sessions keep no capture buffer once it is submitted (captures are told apart by their source timestamp): ScreenCaptureKit delivers into a queue of three surfaces, and Tier 2 run 41587067703 stalled after 11 captures while each tile session held the last captures it had encoded and skipped.
- **Convergence.** The encoder gives the host its refinement policy (`refinementPolicy`, read on every refinement output, so after a fallback the host follows VideoToolbox's `.standard`). From the bottom of Apple's ladder up, VCP's ends a tile's refinement at its first pass under 200 bytes (`convergedRefinementBytes`); below it, where refinements stay at QP 28, all four passes run: after the QP-6 pass, later passes of a typed tile are ~120-byte frames that change nothing. In host-lab run 41693588462 (tamale, 4K typing) that cut tile encodes from 1,344 to 1,060 and the host's CPU from 16.0% + 8.0% (VTEncoderXPCService) to 13.5% + 6.5%; VideoToolbox there was 6.4% + 3.6%. VCP costs about 1 ms more CPU per tile encode than VideoToolbox, inside VideoProcessing.
- **Decoding.** The viewer decodes a 4:4:4 stream in the range its format description signals, so VCP's full-range tiles decode to `444f` and no range conversion happens in the decoder. Decoding them to 4:4:4 video range put Tier 2 whites at 253 instead of 255 on croissant's M6 (run 41665274823, every level scaled by about 0.992), which held VCP's test-card `psnr_y` near 42 dB however sharp the tiles were; an M1 Pro converts exactly, and the encode lab, which decodes in full range, never showed it.
- **References and recovery.** Each session marks the pictures it wants acknowledged with `RequireAcknowledgementToken`, which rides as the tile's `ltrToken`; acknowledged tokens go back with that tile's next encode as `AcknowledgedTokens`. Refreshes are per tile: `ForceKeyFrame` or `ForceLTRRefresh`.
- **Network inputs for E6.** `setNetworkFeedback` passes `PacketErrorRate`, `RoundTripDelay` (ms) and `AverageTransmissionBitRate` with every frame. The three keys are optional: a macOS without them still runs VCP, without the inputs. Offline they left the bitstream byte-identical (they appear to drive Apple's FEC and packetisation, which `codevisor-media` doesn't use), so their units are unverified.
- **Fallback.** `ScreenSharingFallbackTileEncoder` wraps VCP and a factory for the public VideoToolbox encoder with the same layout, which it builds only when VCP first fails (851-4081). An encode VCP refuses goes to VideoToolbox in the same call; a VCP failure reported later is passed to the host once, and every later output VCP still produces becomes a failure, so the host encodes those tiles again one frame interval later, from VideoToolbox (each tile's first VideoToolbox frame is a keyframe). Acknowledgements after the fallback reach VideoToolbox only for tokens it issued. Metrics: `encoderFallbacks`, `encoderFallbackReason`, `encoderFallbackBuild` (building the VideoToolbox encoder), `encoderFallbackBuildError`, `encoderFallbackToKeyframe` (failure → first VideoToolbox tile). The viewer rebuilds a stream's decoder when its parameter sets change, so 4:4:4 → 4:2:0 at the fallback needs nothing else. Before the sessions start, a self-test loads the symbols and encodes a 512×256 four-tile frame; a failure there also selects VideoToolbox, and its outcome is kept for the life of the process. Decisions: the VideoToolbox encoder is built at the first failure, not up front, so a VCP share holds no idle VideoToolbox sessions (at 4K, built up front it held 4 next to VCP's 4 tiles, about 12 of the hardware's low-latency sessions, and some Macs have only 4–5). The first VideoToolbox session in a process costs 1–3 s (M1 Pro), so `ScreenSharingV2Encoders` warms VideoToolbox once per process in the background, opening and closing one small session, when it starts VCP. After that, the tile encoder opens its sessions in parallel in about 10–20 ms. On an M1 Pro at 4K, failure to first VideoToolbox tile took 64–75 ms built lazily against 55–62 ms built up front (build 12 ms), and a fresh session's first keyframe costs the same either way. An encode VCP refuses builds the fallback in that call; a failure VCP reports in a callback reaches the host at once and starts the build on its own queue, so the host's re-encode a frame interval later finds it ready. A build that fails (no hardware session free) closes the sessions it opened and fails that encode, and the next build waits a second; `setBitrate` only stores the rate, which each build applies; after a fallback the capture stays BGRA, which VideoToolbox converts itself; any error from VCP, including one VideoToolbox would also hit, ends VCP for the session.

Probes (local M1 Pro, macOS 27.2, behaviour only): `xf44` and `444f` sources give 4:4:4, `420v` gives 4:2:0, BGRA is refused (-12902); `EnableFrameDropping` can't be set; `DirtyRects` changed nothing. The encoder lab's "blurry after changes" result (test cards SSIM min 0.65) came from VCP rows run without refinement while the VideoToolbox rows had four passes. On tamale (encode-lab run 41557954805, 4K, 4 tiles, 45 Mbit/s with a 50 ms limit) four passes lift test cards from 32.9 to 40.1 dB PSNR-Y (SSIM mean 0.897 → 0.929; the minimum, 0.646, is the frame of the change itself) and take idle-cursor from 0.46 to 0.05 Mbit/s; `DisableDirtyDetection` in the specification changed nothing there either, so VCP's own tile skipping stays and is handled as above.

### Product integration (E8, 851-3823; Mac to Mac's engine since 851-4064; iOS since 851-3824)

**Choosing the engine.** Every viewer, on a Mac or an iPhone/iPad, streams a Mac over engine v2 only (851-3826 removed the WebRTC fallback); there is no setting or environment override (851-4064 removed `CODEVISOR_SCREEN_SHARING_ENGINE` and the Machine Settings → Developer picker; per-machine values stored under `screenSharing.engine.<machine>` are ignored). A host whose `capabilities` reply doesn't list v2 (an older Codevisor) ends the stream with a message to update Codevisor on that Mac, so these viewers can't view hosts that old. The iOS pane (`ScreenSharingStream` in `ScreenSharingPane`) uses the same connector and session as the Mac. The Simulator pane and the Computer Use live preview are v2-only too (see [Simulator and Computer Use streams](#simulator-and-computer-use-streams-851-4089)). `CODEVISOR_SCREEN_SHARING_V2_ENCODER` (`vcp` or `vt`) remains a debugging knob for the host's encoder.

**Signaling.** It stays on the authenticated path (viewer → `POST /v1/screen-sharing` → Unix bridge → host app):

- A host app that has a media endpoint lists `engines: ["v2"]` in its `capabilities` reply. A server or host that predates it strips or omits the field, and the viewer ends with the update message.
- A v2 `start` (or `restart`) carries `engine: "v2"` and `media`, the viewer's endpoint address (endpoint ID, relay URL, direct addresses), and no SDP offer. The server requires a 64-hex endpoint ID, at most 32 addresses of 64 characters and a relay URL of at most 512 characters.
- The host answers `connecting` with `media`: its own endpoint address and a session token (32 random bytes, hex).
- The start also carries `chroma`: `444` when the viewer decodes HEVC Main 4:4:4 (VCP's output), `420` when it doesn't. The viewer finds out once, by decoding a canned 64×64 Main 4:4:4 keyframe with its own decoder settings (`ScreenSharingV2Chroma.decodable`); a host given `420` uses the VideoToolbox 4:2:0 encoder for that viewer instead of VCP. Without the field (an older viewer), the host uses its configured encoder. Apple silicon Macs and the iOS Simulator decode 4:4:4. The iOS pane asks for `420` regardless (`ScreenSharingPaneModel.requestedChroma`) until 4:4:4 decode of a full-size tiled stream is confirmed on an iPhone; the probe decodes on the Simulator, which isn't the hardware decoder.
- If the first attempt can't get an endpoint, gets no grant, can't connect within 15 s or is refused, the viewer ends the stream with a message (no video within 24 s too, unless the host is reporting a notice such as a capture restart). A connection lost after video arrived reconnects (`restart`; the Mac tries at most three times, iOS twelve with a backoff), and a reconnect whose connect fails tries again within those limits.

**Endpoints.** Every app uses the app's tunnel endpoint (`AppEnvironment.screenSharingEndpoint()`, over `CloudTunnelEndpoint.screenSharingEndpoint()`, configured at launch into `ScreenSharingMediaEndpoint.shared`), which binds `codevisor/screen/1` with the media transport config (E2); without cloud sign-in it binds direct-only and stays bound until the app quits. With the cloud on, the endpoint is relay-only until Local Network access is granted, so a Mac asks for it (`setLocalNetworkAccess(.requested)`, which shows macOS's prompt once; iOS leaves that choice to its onboarding step and stays relay-only until it's made) and waits for the rebound endpoint before it sends or answers a v2 start. When the endpoint has neither a relay nor a direct address yet, it waits up to 2 s for one. The host accepts screen connections in one loop per endpoint (`ScreenSharingV2Acceptor`). `ScreenSharingV2SessionRouter` reads each connection's hello and hands the connection, hello replayed, to the session whose token it carries, if that session expects the connection's endpoint ID (which TLS has already authenticated); any other connection is closed, as is one that sends no hello within 10 s. Routing by token lets one viewer Mac hold several sessions on one host, such as a screen and two simulators. An endpoint can't dial itself, so when a grant names the viewer's own endpoint (a Simulator pane showing this Mac's simulator) the Mac viewer connects in memory instead (`ScreenSharingViewerMedia`, which hands the shared connector the acceptor's local route): `ScreenSharingV2LocalConnection` gives the engine, channels and decoder the same streams and media transport without the network, and holds back the host once 8 MiB of encoded video waits for the viewer. A rebind (relay change, the direct-paths toggle, `rebuild()`) drops a live v2 connection, and the viewer reconnects.

**Control plane** (`Session/`). The viewer opens one bidirectional QUIC stream per channel on the media connection; each message is a length-prefixed frame (`codevisor-net`'s message streams, 4 MiB at most). The first stream is control: its first message is the channel byte (1) and the token, and the host answers 1 (accepted) or 0 and a reason. The host compares the token with the session's, so a connection is bound to the lease the start created; only then does the viewer open the others, each starting with its channel byte: clipboard (2), clipboard sharing (3), display (4), video format (5), cursor (6), audio (7), simulator (8, the Simulator pane's touches, buttons and device state). Messages use the encodings the WebRTC data channels used, so `ScreenSharingHostControl`, the clipboard transfer, the cursor publisher and the audio encoder are the same code. Each channel is its own stream, so a 32 MB clipboard transfer never waits behind, or holds up, input. Send buffers are 16 KiB for control and 1 MiB for clipboard; overflowing one closes that channel, as before. Cursor positions and Opus packets go as unreliable datagrams on the media session (kinds 6 and 5); cursor subscriptions and shapes, and audio subscriptions, use their streams. There's no video-refresh channel: the transport's per-frame feedback replaces it.

**Host.** `ScreenSharingV2HostLink` owns the channels, the media session and the engine (`ScreenSharingV2Host` and the encoder `ScreenSharingV2Encoders.make` builds, `CODEVISOR_SCREEN_SHARING_V2_ENCODER` choosing VCP or VideoToolbox). Capture uses `ScreenSharingV2Profile` (native pixels up to 3840×2160, the encoder's pixel format). A display resize (Dynamic Resolution) stops the engine and builds a new encoder for the new size on the same media session and connection; until it's ready, and for captures of the old size after it, frames are dropped. The host service runs the lease, heartbeat, indicator, capture restarts and virtual display around the link, with no adaptive-quality loop (v2's rate control does that job) and streams SDR only.

**Viewer.** `ScreenSharingV2ViewingSession` is a `ScreenSharingViewingSession` like VNC's, so the pane, its reducer and the surfaces are unchanged. Audio plays through the same jitter buffer with a 40 ms target, plus up to 120 ms more after underruns; there's no video jitter buffer to follow.

**Connection Details** (the info button on a Mac, the pane's … menu on iOS) shows Engine (v2 · QUIC), Route (Direct or Relay), receive bitrate, round trip (the selected QUIC path's), decode p95 and Recovery (loss, NACKs, FEC repairs and skipped frames from the media session), then the frame timeline: p50 / p95 per stage over the complete records among the last 600 (`ScreenSharingTimelineBreakdown`, every stage but `jitterBuffer`; `handOff` shows as Hand-off), and capture → screen when host and viewer share a clock or the sum of the stages when they don't. The statistics tick drains the records completed since the previous one (`records(after:)`), once a second, so the media path does no extra work.

**Network changes.** QUIC migrates the connection to the new path (iroh's path selection, with the app's `networkChanged()` telling the endpoint), so a network switch doesn't renegotiate; the session only ends when the QUIC connection closes.

### Simulator and Computer Use streams (851-4089)

`SimulatorStreamHost` and `ComputerUseLivePreviewHost` list `engines: ["v2"]` when the app has a media endpoint and serve a v2 start through `ScreenSharingV2StreamLink`: a `ScreenSharingV2HostLink` plus the token handshake above, with no adaptive-quality loop. The link replays the latest frame once the viewer connects, since a still simulator or window sends none. The Computer Use link answers control requests as view-only, as before.

Both viewers are v2-only on macOS and iOS, as every viewer is: every Simulator pane gets a `SimulatorStreamV2` connector (`SimulatorStreamV2.live`). The macOS app passes the acceptor's in-memory route for its own simulators; iOS passes none. Each viewer asks for the chroma it decodes, as the Screen Sharing viewers do (the Mac probes `ScreenSharingV2Chroma.decodable`; iOS asks for `420`), and the Simulator host picks the encoder from it (`ScreenSharingV2EncoderKind.forViewer`). A host that doesn't list v2 ends the stream with a message to update Codevisor.

The hosts answer only v2 starts (851-3826 deleted their WebRTC peers); the server tells a viewer that still sends an SDP offer to update Codevisor.

## Frame timeline

Every presented frame gets a record of where its time went, following Moonlight: each machine times only its own stages, so no clocks are synchronised. The host measures four stages and sends them with the frame, in v2's in-band frame metadata (`ScreenSharingV2FrameMeta`: capture, admission, encode and hand-off durations, the capture timestamp and the host's clock identity). The viewer times its own stages and joins them to the host's by the frame's content identity, `sourceTimestampNs`.

| Stage | Machine | From → to |
| --- | --- | --- |
| `capture` | host | ScreenCaptureKit display time → capture callback |
| `hostQueue` | host | capture callback → encoder submit (admission) |
| `encode` | host | encoder submit → VideoToolbox output |
| `handOff` | host | encoder output → `send_frame` |
| `network` | estimate | half the selected QUIC path's current round-trip time |
| `assemble` | viewer | the critical tile's first packet in → the update's decoder input (its whole assembly for a one-tile update) |
| `jitterBuffer` | estimate | always 0 for engine v2, which has no video jitter buffer (kept in the record format) |
| `decode` | viewer | decoder input → VideoToolbox output (`decodeSubmitNs` marks the VideoToolbox submit in between) |
| `delivery` | viewer | decoder output → mailbox put |
| `renderQueue` | viewer | mailbox put → Metal command buffer commit |
| `present` | viewer | commit → on glass |

`network` comes from the media connection's statistics, polled once a second, not per frame. An update's host stages and `handOff` are those of the tile that finished last on the host (the critical tile). `decode` starts when the update's first tile reaches the decoder, so `assemble` stops there too and the two never count the same time. Pacing between `send_frame` and the first packet is not timed, so it shows up as residual. On glass is the drawable's `presentedTime` when it is nonzero (`onGlassSource: "presentedTime"`). Some setups report 0 for every drawable (851-3582 §9); there it is the display-link estimate, one refresh after the first refresh at or after the GPU finished the frame (`"displayLinkTarget"`). Every record carries that estimate as `displayLinkTargetNs`, so it can be checked against `presentedTime` and an outside observer. The display link runs at the view's draw rate and the GPU time is the command buffer's `gpuEndTime`; on a MacBook Pro's built-in display the estimate matched `presentedTime` to −0.014 ms at p50 (p5–p95 within 0.03 ms, 1,220 frames). Once any drawable has reported a `presentedTime`, a 0 means the drawable was dropped, and the frame gets no on-glass time. The host also sends a hash of its boot session. When it matches the viewer's, the two share a clock, as on a same-Mac loopback. The record then also carries `captureToPresentUs`, measured end to end, and the summary reports the residual (`captureToPresent − stageSum`) per frame.

`ScreenSharingMetrics.timeline` keeps the last 1,800 records and the last 16 decoded-but-unpresented frames in fixed rings (the record ring is allocated with the first record); recording allocates nothing else and never hops to the main actor. `records(after:)` drains records by sequence number, and `summary()` is the rolling summary (format `version` 2, which added `handOff` and `assemble`): `frames` (records with every stage), `incompleteFrames`, `unpresentedFrames`, and count/p50/p95/max in milliseconds per stage, for `stageSum`, `captureToPresent` and `residual`. Percentiles cover complete records only, so the per-stage numbers and their sum describe the same frames. With `CODEVISOR_SCREEN_SHARING_STATS_LOG=<directory>` set (the dev runner passes it through), the viewer writes one JSON line a second to `<directory>/<viewer id>.jsonl`: `time`, `statistics`, `metrics`, `timeline` (the summary), and `frames`, the records completed since the previous line. A record:

## Benchmark core

`ScreenSharingBench` holds the pure parts of the [screen sharing v2 benchmark](https://linear.app/851/document/screen-sharing-v2-benchmark-design-851-3582-0309dbbc943b) that the scene player, the observer, the loopback and the workflow share. Benchmarks run only from the benchmark workflow, never from `bun run check` or `bun run swift:test`; this target's unit tests do run there. All times are mach continuous time in nanoseconds, and every derived duration is in milliseconds.

- **Barcode.** `BenchBarcode.draw(_:into:layout:)` writes a version (0…2²⁴−1) into a BGRA `CVPixelBuffer` or a CPU-writable `.bgra8Unorm` `MTLTexture`; `BenchBarcode.read(_:layout:)` decodes a BGRA, `420v` or `420f` pixel buffer. The strip is 32 blocks (24-bit version, most significant bit first, then CRC-8 with polynomial 0x1D and initial value 0xFF), one row of data and one row of its complement, `BenchBarcodeLayout.standard` being 16×16-pixel blocks at the top left (512×32 px). Each block compares the mean luma at four central points of its data and complement halves, so no fixed threshold is needed. A read is `.version`, `.ambiguousBlock` (a block's two halves differ by less than 64 code values, as a tear between the rows gives) or `.checksumMismatch`. A read spliced at any block from two versions up to four apart never decodes to a third version (checked exhaustively over all 2²⁴ versions); count unreadable reads, never drop them.
- **Stats.** `BenchDistribution(_:)` is `{count, p50, p95, max}` by nearest rank (`sorted[ceil(p·n) − 1]`), `nil` for no samples. `BenchFrameGaps.intervalsMs(between:)` turns on-glass times into gaps. `BenchFreezes(gapsMs:activeDurationMs:)` applies the W3C rule: a gap of at most 5 s freezes when it is ≥ max(3·avg, avg + 150 ms), where avg is the mean of the previous 30 such gaps, so the first 30 gaps never freeze; a gap over 5 s is a pause, counted apart and left out of the average.
- **Clock.** Give `BenchClockEstimate(bursts:)` the four timestamps of each probe (`BenchClockExchange`), grouped by burst. It keeps each burst's minimum-round-trip probe, fits offset and drift by least squares, and maps `localNs(fromRemote:)`. `quality` is the report's `{epsilon_ms, drift_ppm, residual_ms}`: ε is the largest kept round trip / 2, the residual the largest distance from the fit.
- **Network.** `BenchNetworkModel(conditions:seed:)` follows WebRTC's `SimulatedNetwork`: a packet queue of `queueLengthPackets` drained at `linkCapacityKbps`, then a delay of `delayMs` with normal jitter of `delayStandardDeviationMs` that never reorders. Loss is Bernoulli or, with `averageBurstLossLength`, Gilbert–Elliott (`BenchLossModel`). Loss is drawn for every packet offered, from its own `SplitMix64` stream, so the loss pattern depends only on the seed and packet index. `BenchNetworkConditions.matrix` is N0–N7.
- **Report.** `BenchReport` is `codevisor.screen-sharing.bench/v1`. `BenchReportCodec` encodes it with snake_case keys (a capital starts a word; digits stay with the word before), sorted, ISO 8601 dates (read with or without fractional seconds), absent values left out and seeds below 2⁵³ so JavaScript reads them exactly, and refuses a report whose `validationIssues` aren't empty. `Tests/ScreenSharingBenchTests/Report/Fixtures/report.json` is the golden file. Systems are `apple-hp`, `codevisor-v2` and `codevisor-v2-vcp`; `codevisor` (engine v1, which the bench no longer runs since 851-3826) still decodes, so older reports and the results branch's index read. A `BenchComparison`'s `system` names the Codevisor system compared with Apple HP (absent means `codevisor`). Engine v2 adds optional fields only, so the schema stays v1: `BenchFrameTimestamps.media` (send call, first and last packet out, first packet in, recovery), `BenchStageTimings.media` (`BenchMediaStages`: hand-off, queue, send, network, assemble, recover) and `BenchResult.media` (`BenchMediaCounters`, including the host's requested refreshes and keyframes and the viewer's stalled tiles).
- **Clock track.** `BenchClockTrack(bursts:halfWindowNs:)` keeps each burst's minimum-round-trip probe like `BenchClockEstimate`, but maps times with a line fitted only to the bursts within ±30 s (or the nearest two), because the minis' relative clock rate wanders by several ppm with load. Bursts whose round trip / 2 is over both twice the run's median and 0.25 ms are left out (`rejectedBursts`): every probe in them queued behind something, so their offset error can reach their whole round trip / 2. `quality.residualMs` is the largest distance of a kept burst from the line fitted to its neighbours without it; `linearResidualMs` is the single-line residual for comparison.
- **Clock probes.** `BenchClockProbeResponder(port:)` answers, and `BenchClockProbeClient(responder:).burst()` sends 16 probes one at a time and returns their `BenchClockExchange`s. A probe is 40 bytes: `CVCP`, version 1, kind (1 request, 2 reply), two zero bytes, then the sequence, client send, responder receive and responder send times as big-endian 64-bit integers. Receive times come from the kernel (`SO_TIMESTAMP_MONOTONIC`) and send times are read just before `sendto`. A reply to an earlier probe is skipped, and a probe whose send or receive fails counts as lost (`lastError` keeps the error); the responder counts its failures and keeps serving. `BenchMachClock` reads the continuous clock and converts mach absolute times to it (`BenchClockOffsetRead` brackets one continuous read between two absolute reads).
- **Usage.** `BenchProcessUsage.sample(pid:)` reads `proc_pid_rusage` (`RUSAGE_INFO_V6`; its CPU times are mach ticks, converted to ns), and `BenchProcessLoad(from:to:)` is CPU % of one core and power in mW. `BenchProcesses.pids(named:)` finds processes by name. `BenchInterfaceCounters.sample(interface:)` reads an interface's 64-bit byte counters (`NET_RT_IFLIST2`), and `BenchInterfaceRate(from:to:)` is Mbit/s each way.
- **Observer.** `BenchCapturedFrame.observation(of:layout:callbackNs:)` turns a complete ScreenCaptureKit frame into a `BenchObservation` (PTS converted to continuous time, the callback time, and the version or why it was unreadable); other frame statuses give `nil`. `BenchObserverLog` is the observer's JSONL: a header (`codevisor.screen-sharing.bench.observer/v1`, `clock: mach_continuous_ns`, the continuous − absolute offset, the machine, the source and the observer's CPU), then one line per frame. `BenchObservedVersions` keeps each version's first PTS (its on-glass time) and the unreadable fraction; `BenchObserverAgreement` is C1, and `BenchInputResponses` pairs each input event with the first frame showing another version than the one on screen at the event (C6 and S7's input to photon). An event before any readable frame, or whose change lands after the next event (or after a previous event whose change hadn't landed yet), is unanswered rather than guessed. `BenchInputToPhoton` applies it to a run's `BenchInputEvent` log (each event's kind and post time) and splits the delays by kind; `BenchInputSchedule` is the seeded order and spacing of the events (150–350 ms).
- **Gate.** `BenchRegressionGate.regressions(baseline:first:second:)` takes `BenchGateSample`s for one scene and network: the baseline nights (the last 7 count, compared by median) and two consecutive runs. A metric regresses only when both runs pass its threshold: e2e p50 up by more than max(15%, 3 ms), p95 up by more than max(20%, 5 ms), updates/s down by more than 5%, freeze ratio up by more than 2 points (pass it for N3 only), `psnr_y` down by more than 0.5 dB, or an encode or decode error in both runs.

Control API references: [Apple’s private event-source state](https://developer.apple.com/documentation/coregraphics/cgeventsourcestateid), and [event-source user data](https://developer.apple.com/documentation/coregraphics/cgeventsource/userdata).
