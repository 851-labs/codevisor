# Screen sharing

The engine behind the Screen Sharing pane, in four targets under `packages/swift/ScreenSharing`:

| Target | Links | Holds |
| --- | --- | --- |
| `ScreenSharing` | CZlib, system frameworks | `Session/` (viewing-session and message-channel contracts), `Messages/` (input, control, clipboard, refresh), `Frames/` (frame, mailbox, sink, identity), `Metrics/`, `Capture/` (ScreenCaptureKit, the source idle monitor), `Codecs/` (VideoToolbox encoder and decoder), `Render/` (the Metal view and coordinator), `Viewer/` (the AppKit surface: video, input capture, forwarder), `HostInput/` (control lease, CGEvent injection), `RFB/` (the VNC wire protocol), `VNC/` (VNC as a viewing session), `Audio/` (Opus encoding, jitter buffer, playback), `Tunnel/` (SDP for tunnelled media) |
| `ScreenSharingWebRTC` | `ScreenSharing`, WebRTC | `Peer/`, `Channels/` (data channel, frame sender), `Endpoints/` (sender, receiver, recovery), `Codecs/` (the factory bridging VideoToolbox into WebRTC), `FieldTrials/`. The only target that links the binary framework. |
| `ScreenSharingTesting` | `ScreenSharing`, `ScreenSharingBench` | The in-process RFB server the suites drive and the replay of recorded RFB fixtures. Never a dependency of a product target. |
| `ScreenSharingBench` | system frameworks | The benchmark core (see [Benchmark core](#benchmark-core)): `Barcode/`, `Stats/`, `Clock/`, `Network/`, `Report/`, `Gate/`. Pure logic, no UI. Never a dependency of a product target. |

Folders are layers; targets are dependency edges. `ScreenSharing` cannot reach WebRTC because it does not link it, so the VNC session, the viewer surface and every test of those parts never load the framework. `Viewer/`, `HostInput/` and `VNC/` are macOS-only (`#if os(macOS)`); the rest compiles for iOS. Product feature code (the Composable Architecture reducer, the backends and runners, the host service) stays in `CodevisorCoreMac/ScreenSharing`.

## Native Screen Sharing

A native media library and a native macOS workspace pane with authenticated signaling and explicit remote control. No HTTP plugin server or webview participates in video delivery.

The working path is ScreenCaptureKit → native WebRTC video source → custom VideoToolbox encoder → encrypted WebRTC media → custom VideoToolbox decoder → CVPixelBuffer-backed Metal textures. The custom codec factories are used by WebRTC itself; frames are not encoded twice. Peers prefer HEVC Main 4:4:4, then HEVC Main, then H.264, and each offers only the codecs its Mac decodes in hardware (H.264 always).

## Native workspace pane

Run `bun run dev:macos`. In a workspace hosted by a Mac, open New Tab → Screen Sharing and select a display from the searchable chooser to connect. The host must run this version of the native app and allow Screen Recording. The native toolbar shows the machine name and resolution, View/Control, clipboard and connection details. The video always scales to fit the pane. Closing the tab ends the session.

The viewer sends a receive-only offer through the existing machine-authenticated, relay-aware client to `POST /v1/screen-sharing`. The server validates the active workspace and native pane, then forwards the request over Codevisor’s authenticated Unix bridge to the app’s native host service. SDP stays transient; only the stable display UUID and fit preference enter pane metadata. Synced size preferences update the existing native surface; a display change from another client requires a fresh Connect. Websites are rejected even on loopback.

One viewer owns the host at a time. Capture begins after its peer connects. The host shows a menu-bar Sharing indicator with Stop Sharing. An eight-second heartbeat renews a 25-second lease; loss of the viewer stops capture. Sleep, session deactivation, display changes and SCK errors also stop it. A connection without video ends after three heartbeat intervals, and decoder failures end viewing on the next heartbeat. Hiding the viewer (switching tabs) keeps the connection for five minutes, like Apple Screen Sharing's window: control is given back at once, and returning shows the live picture and asks for control again without renegotiating. Closing the viewer, or hiding it for longer, tears down media; returning then renegotiates. A start from the same pane replaces that pane's earlier session if its stop hasn't reached the host yet, rather than finding the host busy. A newer negotiation waits for the old stop request, and generation checks reject late frames and signaling responses. Reopening the app requires an explicit Connect.

The host captures the physical display scaled to fit 2560×1440, preserving aspect ratio, at up to 60 fps with a 45 Mbps bitrate ceiling. When the viewer asks for a size on `codevisor.display.v1`, the host mirrors the display onto a HiDPI virtual display of that size (at most 1920×1080 points) and captures that instead; restoring returns to the physical display. Direct ICE is the default. Optional host-configured STUN/TURN supports other routes; the existing cloud channel still carries signaling only. See connectivity configuration below.

## Native control

New panes start in **Control** mode and request control when video and the data channel are ready. The selector stays interactive while connecting; choosing **View** cancels that pending request. The selected mode survives menu interactions and reconnection. The host also needs Accessibility permission (called Device Control and Data Access in macOS 27). Control doesn't take the keyboard: input goes to the host once the video is clicked, so arriving at the pane by keyboard (⌘[ through the sidebar, a tab switch) leaves the app's shortcuts working. **Control–Option–Escape** hands the keyboard back to the app and stays in Control; choosing **View** gives control back. Clicking outside the video or losing keyboard/window focus suspends input forwarding and releases held input without changing the selected mode. Hiding the pane gives the control lease back (it is requested again when the pane is shown); closing it, disconnecting, and the host’s Stop Sharing action tear down the connection and its control lease. A denial, revocation or input failure keeps **Control** selected and shows why, with Request Control to try again; only the user’s own release (choosing View) switches to **View**. The host indicator changes to “Controlled” while a control lease is active.

A fresh host-issued control lease binds input to the current authenticated WebRTC peer and selected display. One-second heartbeats renew a separate three-second control deadline, checked every 250 ms. Expiry, permission loss, malformed messages and channel closure revoke the lease and release tracked keys/buttons. Delayed grants are released after viewer cancellation; input from an expired lease cannot revive control. No control lease, input or key content enters pane metadata or logs.

The native ordered data channel carries key/button transitions, scroll deltas and motion. A 16 ms viewer tick coalesces waiting motion; transitions flush it first to preserve ordering. Each button event contains its own normalized coordinates. The send queue admits at most 16 KiB, and the receive queue at most 256 messages / 64 KiB; congestion or invalid input closes control instead of accumulating actions. This first implementation deliberately uses one reliable ordered channel. A separate unreliable motion channel needs button-generation coordination before it can replace this ordering contract.

The native surface maps through fit-to-pane letterboxing and backing-pixel scale. The host maps normalized coordinates into Quartz display bounds, including negative origins. It uses public CGEvents from a private event source, with no automation delays or app activation. Tagged injected events are excluded from capture by a viewer on the same Mac. Fractional trackpad deltas accumulate before conversion to integer pixels.

Physical Mac key codes use the host’s keyboard layout and input method. With viewer Accessibility permission, a focused video surface in Control mode forwards system shortcuts such as Command-Space and Command-Q. Without it, control still works and those shortcuts stay on the viewing Mac; a Mac host's pane says so, naming that Mac and the app to allow. A Linux desktop needs no permission. Physical typing, modifiers, repeat, mouse buttons, dragging and scrolling are forwarded; there is no dedicated Unicode composition UI. The clipboard is shared automatically, with explicit transfer as the alternative (below). The protocol also has a bounded, separate text-insertion message.

## Clipboard, cursor, audio and connection details

Whatever can be copied and pasted on a Mac (images, rich text, HTML, app-specific formats, several items at once) moves between clipboards, up to 32 MB, in one of two ways, chosen per machine from the clipboard menu. **Use Shared Clipboard** (the default) works like Apple Screen Sharing's: while the viewer controls the host, a copy on either Mac reaches the other however it was made (keys, Edit menu, context menu). Each side checks its pasteboard's change count every 250 ms, which never reads the contents, and reads the contents only after a copy: every type each item itself provides, not the conversions the pasteboard server synthesizes (a screenshot sends its PNG, not a TIFF copy too). The host sends its copies once the viewer asks on `codevisor.clipboard-sharing.v1`, and only those made after it asked. The viewer sends a copy made elsewhere when the video has keyboard focus in a key window, so a paste on the host already has it. A copy a side wrote for the other never bounces back; when both copy at once the viewer's copy wins. Items marked concealed, transient or auto-generated (nspasteboard.org, as password managers do) are never shared. A host that predates the channel still receives the viewer's copies but doesn't send its own; turn sharing off for **Send Clipboard** and **Get Clipboard** there. With sharing off, those menu items move the clipboard one way on request.

Either way, a separate ordered SCTP channel carries the transfer; it cannot fill the keyboard/mouse channel. The viewer announces rich content in its `codevisor.clipboard-sharing.v1` message (an optional field older hosts ignore), and a host that understands it answers. Until both sides know, and always with a host, viewer or VNC server that predates it, only plain text (64 KiB of UTF-8) moves, in 2 KiB chunks with stop-and-wait acknowledgments, byte-for-byte the format older peers decode. Rich content is the items' types and data in a binary property list, sent in 48 KiB chunks with up to eight unacknowledged. A transfer that makes no progress for ten seconds expires. Invalid or incomplete data is rejected, and partial data is discarded on cancellation. A download cannot replace a newer local copy made while it was in flight. File URLs and file promises stay on the Mac that copied them (there is no file transfer), and nothing reaches signaling, logs or the workspace database.

A Linux desktop that `codevisor-server` set up (`desktop: "xfce"` in `screen-sharing.json`) gets the same rich clipboard without VNC's text-only cut text. The server announces it with a `clipboard-host` text frame on the VNC WebSocket, next to the control lease, and then carries the same transfer messages there; the Mac stops sharing RFB cut text and relays its clipboard channel through those frames. The server reads and writes the X clipboard with `xclip` (PNG, JPEG, GIF, HTML, RTF and UTF-8 text) and learns of copies from XFixes selection events through a small `python3` ctypes helper, so it never polls. X lets one `xclip` serve only one type, so a paste on the desktop gets the best single type the Mac copied: an image if there is one, otherwise text, then HTML, then RTF. A Mac item with only TIFF is sent as PNG. Without `xclip`, `python3` or XFixes the server doesn't announce, and the desktop keeps VNC's plain-text clipboard.

ScreenCaptureKit includes the host cursor in video until the viewer subscribes on `codevisor.cursor.v1`. The host then stops capturing the cursor and publishes its position about 120 times a second, with its shape and scale, and the viewer draws it as an overlay. If the channel closes, the cursor returns to the video. AppKit cursor rectangles suppress the viewer cursor only inside the active control surface and restore the local arrow on release/exit.

System audio is captured by ScreenCaptureKit (excluding Codevisor's own) only while the viewer subscribes on the unreliable `codevisor.audio.v1` channel. The host encodes it as 48 kHz stereo Opus; the viewer buffers and plays it.

Connection Details shows the selected direct/relay route, transport, decoded resolution, interval presentation rate, receive bitrate, round-trip time and decode p95. It omits SDP, addresses and credentials. Statistics run separately from the control heartbeat.

## Connectivity and recovery

The native host reads optional deployment configuration from its launch environment:

| Variable | Meaning |
| --- | --- |
| `CODEVISOR_SCREEN_SHARING_STUN_URLS` | Comma-separated `stun:` or `stuns:` URLs |
| `CODEVISOR_SCREEN_SHARING_TURN_URLS` | Comma-separated `turn:` or `turns:` URLs, optionally `?transport=udp` or `?transport=tcp` |
| `CODEVISOR_SCREEN_SHARING_TURN_SECRET` | Host-only TURN REST shared secret; never shipped in the viewer |
| `CODEVISOR_SCREEN_SHARING_RELAY_ONLY` | `1` forces a TURN route; default `0` allows direct connections |

With no configuration, neither peer contacts a third-party ICE server. The host mints five-minute, viewer-specific TURN REST credentials using HMAC-SHA1. The viewer requests fresh credentials immediately before negotiation through the authenticated, uncached machine API. This matches [coturn's TURN REST mechanism](https://github.com/coturn/coturn/blob/master/README.turnserver#turn-rest-api). No relay infrastructure or fixed client secret ships with Codevisor.

After an established connection drops, the viewer releases input, discards the old native peer and its frame mailbox, and renegotiates using `restart`. The host accepts replacement only for the same still-live viewer lease and display. Host stop, sleep, display change, cancellation and lease expiry prevent renewal. Replacement uses fresh ICE/DTLS and codec state rather than restarting ICE inside the old peer; control must be requested again. Three automatic replacements are allowed before explicit reconnect is required. This avoids replaying queued input or decoder state across routes.

The host polls WebRTC's selected candidate-pair bandwidth estimate once per second. Two seconds of insufficient bandwidth lowers one quality step: full resolution at 60 fps → full resolution at 30 fps → 75% dimensions at 30 fps → 50% dimensions at 20 fps. Fifteen seconds of sustained headroom restores one step. Capture and the native source change together; old-size raw frames are discarded before encoding. Coordinates remain normalized to the original display. Missing estimates leave the current quality unchanged.

Transport keyframe requests remain pending through bounded-pool admission drops and VideoToolbox completion. Only usable keyframe output delivered to the encoder callback fulfills a request. One forced attempt is allowed in flight; dropped, failed or unusable output retries on a later input frame. Request generations prevent an older keyframe from clearing a newer request, and attempt identifiers reject stale completions.

Trailing packet loss before the desktop goes idle produces no decoder error, no later sequence gap and, in the pinned M152 sources, the same single PLI that a healthy idle transition produces. So every encoded frame carries its content identity, the capture timestamp, in a zero-byte-free user-data SEI NAL unit (30 bytes for H.264, 31 for HEVC). The identity is attached to the pixel buffer by `ScreenSharingFrameSender`, because WebRTC's native source truncates and translates the submitted timestamp before the encoder sees it; the transport encoder refuses input without it through the `encoderError` lifecycle, and the decoder reads and strips the marker before VideoToolbox.

After 100 ms without a capture submission the host re-offers a latest capture that was never encoded (four times at the threshold, then every 2 s until it is encoded, replaced or the peer closes) and then sends one `sourceIdle` notice over the video-refresh channel. The viewer compares the announced identity with its newest decoded one; if older it waits a 100 ms grace, extended by up to four more windows while strictly newer content keeps arriving (at most 500 ms after the notice), then requests a keyframe through the recovery path, keeps the target until that content is decoded, and retries stale completions with a 100 ms to 5 s backoff. Healthy idle costs one wake per 100 ms of activity, one nine-byte message per idle transition and no encode.

The receiver also requests a refresh over the bounded negotiated `codevisor.video-refresh.v1` SCTP stream (ID 4) before its first decoded keyframe and after decoder failure. Both endpoints rate-limit refreshes to at most ten per second. The sender retains at most one capture buffer and resubmits it with a strictly increasing host-clock timestamp, forcing a keyframe, so an idle desktop can recover without new ScreenCaptureKit output. Pending recovery retries stop after a successfully decoded keyframe; normal idle screens have no refresh timer. Decoder generations reject stale completions, and VT callback errors schedule session reset on the decoder queue. Close and format changes release the cached buffer. This adds one retained capture surface.

## Ownership and limits

- Capture callbacks feed WebRTC on the capture queue, without per-frame main-actor tasks. SCK uses a queue depth of three.
- Hardware acceleration is required at VideoToolbox session creation. Software fallback is disabled.
- HEVC Main 4:4:4 (8-bit SDR, 10-bit for HDR) uses standard rate control tuned for speed. HEVC Main and H.264 Baseline use low-latency rate control up to 2560×1440 pixels. There is no B-frame reordering, and keyframes come every 60 seconds unless one is requested. Input dimensions are even and bounded to 3840×2160; the frame rate is at most 60.
- WebRTC handles packetization, congestion feedback, pacing and keyframe requests. Bitrate updates reach VT; the native host adapts capture resolution/frame rate as described above. The app's WebRTC field trials force a zero playout delay (min and max 0: in M152 every frame is decoded and rendered as soon as it is complete, with no 8 ms decode pacing), set the pacing factor to 10 and disable the frame dropper.
- The encoder admits at most three pending raw frames. VT owns each output callback's immutable metadata. The decoder runs synchronously on WebRTC's decoder queue. These bounds describe Codevisor-owned stages; WebRTC also has internal queues and jitter buffering.
- Rendering has a one-frame mailbox, one command buffer in flight, and one retained last frame for resize redraw. Slow consumers replace stale waiting frames. CVPixelBuffers and their Metal textures survive until the GPU completes its reads.
- The peer and capture owner must call `close()` / `stop()`. Closing the peer stops capture-frame admission and remote rendering before disconnecting. The native viewer backend implements reconnect, the heartbeat watchdog and hidden-pane teardown.
- The package is split at the WebRTC seam (see the layout table above). `ScreenSharing` holds frames, the mailbox, metrics, the input/control/clipboard messages, the clipboard transfer, the `ScreenSharingMessageChannel` contract (one negotiated data channel today, an in-memory pair in tests), the `ScreenSharingViewingSession` contract a viewer renders from, and by stage folder `Capture/` (ScreenCaptureKit), `Codecs/` (VideoToolbox) and `Render/` (the Metal renderer, which draws biplanar YCbCr and packed BGRA frames). `ScreenSharingWebRTC` adds the `ScreenSharingSender` and `ScreenSharingReceiver` over a shared `ScreenSharingPeer` base, with their recovery objects and `ScreenSharingPeerOptions`; capture delivers into it through the `ScreenSharingFrameSink` protocol. The receiver is itself the `ScreenSharingViewingSession` a viewer renders from; `VNCScreenSharingSession` (`VNC/`) is the other implementation, over the `RFB/` protocol. The viewer feature in `CodevisorCoreMac` is a Composable Architecture reducer over a `ScreenSharingViewerBackend` (the native backend owns signaling) with the control lease as a child reducer over a `ScreenSharingEndpointClient`; input events stay on the data plane inside the endpoint.

Run the suites with `bun run swift:test`; `bun run check` runs them with the rest of the repository's checks.

## Frame timeline

Every presented frame gets a record of where its time went, following Moonlight: each machine times only its own stages, so no clocks are synchronised. The host measures three stages and sends them inside the frame, in a second SEI next to the content identity (same identifier, a kind byte of `0x81`, 7-bit groups so it never needs emulation prevention). Viewers that predate it strip it with the identity SEI and ignore it. The viewer times its own stages and joins them to the host's by the frame's content identity, `sourceTimestampNs`.

| Stage | Machine | From → to |
| --- | --- | --- |
| `capture` | host | ScreenCaptureKit display time → capture callback |
| `hostQueue` | host | capture callback → encoder submit (WebRTC's source and encoder queue) |
| `encode` | host | encoder submit → VideoToolbox output |
| `network` | estimate | half the selected candidate pair's current round-trip time |
| `jitterBuffer` | estimate | WebRTC's mean jitter-buffer delay over the last statistics interval |
| `decode` | viewer | decoder input → VideoToolbox output (`decodeSubmitNs` marks the VideoToolbox submit in between) |
| `delivery` | viewer | decoder output → WebRTC renderer callback (mailbox put) |
| `renderQueue` | viewer | mailbox put → Metal command buffer commit |
| `present` | viewer | commit → on glass |

`network` and `jitterBuffer` come from WebRTC statistics, polled once a second, not per frame. Packetization and pacing after the encoder are not timed, so they show up as residual. On glass is the drawable's `presentedTime` when it is nonzero (`onGlassSource: "presentedTime"`). Some setups report 0 for every drawable (851-3582 §9); there it is the display-link estimate, one refresh after the first refresh at or after the GPU finished the frame (`"displayLinkTarget"`). Every record carries that estimate as `displayLinkTargetNs`, so it can be checked against `presentedTime` and an outside observer. The display link runs at the view's draw rate and the GPU time is the command buffer's `gpuEndTime`; on a MacBook Pro's built-in display the estimate matched `presentedTime` to −0.014 ms at p50 (p5–p95 within 0.03 ms, 1,220 frames). Once any drawable has reported a `presentedTime`, a 0 means the drawable was dropped, and the frame gets no on-glass time. The host also sends a hash of its boot session. When it matches the viewer's, the two share a clock, as on a same-Mac loopback. The record then also carries `captureToPresentUs`, measured end to end, and the summary reports the residual (`captureToPresent − stageSum`) per frame.

`ScreenSharingMetrics.timeline` keeps the last 1,800 records and the last 16 decoded-but-unpresented frames in fixed rings (the record ring is allocated with the first record); recording allocates nothing else and never hops to the main actor. `records(after:)` drains records by sequence number, and `summary()` is the rolling summary (format `version` 1): `frames` (records with every stage), `incompleteFrames`, `unpresentedFrames`, and count/p50/p95/max in milliseconds per stage, for `stageSum`, `captureToPresent` and `residual`. Percentiles cover complete records only, so the per-stage numbers and their sum describe the same frames. With `CODEVISOR_SCREEN_SHARING_STATS_LOG=<directory>` set (the dev runner passes it through), the viewer writes one JSON line a second to `<directory>/<viewer id>.jsonl`: `time`, `statistics`, `metrics`, `timeline` (the summary), and `frames`, the records completed since the previous line. ## Benchmark core

`ScreenSharingBench` holds the pure parts of the [screen sharing v2 benchmark](https://linear.app/851/document/screen-sharing-v2-benchmark-design-851-3582-0309dbbc943b) that the scene player, the observer, the loopback and the workflow share. Benchmarks run only from the benchmark workflow, never from `bun run check` or `bun run swift:test`; this target's unit tests do run there. All times are mach continuous time in nanoseconds, and every derived duration is in milliseconds.

- **Barcode.** `BenchBarcode.draw(_:into:layout:)` writes a version (0…2²⁴−1) into a BGRA `CVPixelBuffer` or a CPU-writable `.bgra8Unorm` `MTLTexture`; `BenchBarcode.read(_:layout:)` decodes a BGRA, `420v` or `420f` pixel buffer. The strip is 32 blocks (24-bit version, most significant bit first, then CRC-8 with polynomial 0x1D and initial value 0xFF), one row of data and one row of its complement, `BenchBarcodeLayout.standard` being 16×16-pixel blocks at the top left (512×32 px). Each block compares the mean luma at four central points of its data and complement halves, so no fixed threshold is needed. A read is `.version`, `.ambiguousBlock` (a block's two halves differ by less than 64 code values, as a tear between the rows gives) or `.checksumMismatch`. A read spliced at any block from two versions up to four apart never decodes to a third version (checked exhaustively over all 2²⁴ versions); count unreadable reads, never drop them.
- **Stats.** `BenchDistribution(_:)` is `{count, p50, p95, max}` by nearest rank (`sorted[ceil(p·n) − 1]`), `nil` for no samples. `BenchFrameGaps.intervalsMs(between:)` turns on-glass times into gaps. `BenchFreezes(gapsMs:activeDurationMs:)` applies the W3C rule: a gap of at most 5 s freezes when it is ≥ max(3·avg, avg + 150 ms), where avg is the mean of the previous 30 such gaps, so the first 30 gaps never freeze; a gap over 5 s is a pause, counted apart and left out of the average.
- **Clock.** Give `BenchClockEstimate(bursts:)` the four timestamps of each probe (`BenchClockExchange`), grouped by burst. It keeps each burst's minimum-round-trip probe, fits offset and drift by least squares, and maps `localNs(fromRemote:)`. `quality` is the report's `{epsilon_ms, drift_ppm, residual_ms}`: ε is the largest kept round trip / 2, the residual the largest distance from the fit.
- **Network.** `BenchNetworkModel(conditions:seed:)` follows WebRTC's `SimulatedNetwork`: a packet queue of `queueLengthPackets` drained at `linkCapacityKbps`, then a delay of `delayMs` with normal jitter of `delayStandardDeviationMs` that never reorders. Loss is Bernoulli or, with `averageBurstLossLength`, Gilbert–Elliott (`BenchLossModel`). Loss is drawn for every packet offered, from its own `SplitMix64` stream, so the loss pattern depends only on the seed and packet index. `BenchNetworkConditions.matrix` is N0–N7.
- **Report.** `BenchReport` is `codevisor.screen-sharing.bench/v1`. `BenchReportCodec` encodes it with snake_case keys (a capital starts a word; digits stay with the word before), sorted, ISO 8601 dates (read with or without fractional seconds), absent values left out and seeds below 2⁵³ so JavaScript reads them exactly, and refuses a report whose `validationIssues` aren't empty. `Tests/ScreenSharingBenchTests/Report/Fixtures/report.json` is the golden file.
- **Clock track.** `BenchClockTrack(bursts:halfWindowNs:)` keeps each burst's minimum-round-trip probe like `BenchClockEstimate`, but maps times with a line fitted only to the bursts within ±30 s (or the nearest two), because the minis' relative clock rate wanders by several ppm with load. Bursts whose round trip / 2 is over both twice the run's median and 0.25 ms are left out (`rejectedBursts`): every probe in them queued behind something, so their offset error can reach their whole round trip / 2. `quality.residualMs` is the largest distance of a kept burst from the line fitted to its neighbours without it; `linearResidualMs` is the single-line residual for comparison.
- **Clock probes.** `BenchClockProbeResponder(port:)` answers, and `BenchClockProbeClient(responder:).burst()` sends 16 probes one at a time and returns their `BenchClockExchange`s. A probe is 40 bytes: `CVCP`, version 1, kind (1 request, 2 reply), two zero bytes, then the sequence, client send, responder receive and responder send times as big-endian 64-bit integers. Receive times come from the kernel (`SO_TIMESTAMP_MONOTONIC`) and send times are read just before `sendto`. A reply to an earlier probe is skipped, and a probe whose send or receive fails counts as lost (`lastError` keeps the error); the responder counts its failures and keeps serving. `BenchMachClock` reads the continuous clock and converts mach absolute times to it (`BenchClockOffsetRead` brackets one continuous read between two absolute reads).
- **Usage.** `BenchProcessUsage.sample(pid:)` reads `proc_pid_rusage` (`RUSAGE_INFO_V6`; its CPU times are mach ticks, converted to ns), and `BenchProcessLoad(from:to:)` is CPU % of one core and power in mW. `BenchProcesses.pids(named:)` finds processes by name. `BenchInterfaceCounters.sample(interface:)` reads an interface's 64-bit byte counters (`NET_RT_IFLIST2`), and `BenchInterfaceRate(from:to:)` is Mbit/s each way.
- **Observer.** `BenchCapturedFrame.observation(of:layout:callbackNs:)` turns a complete ScreenCaptureKit frame into a `BenchObservation` (PTS converted to continuous time, the callback time, and the version or why it was unreadable); other frame statuses give `nil`. `BenchObserverLog` is the observer's JSONL: a header (`codevisor.screen-sharing.bench.observer/v1`, `clock: mach_continuous_ns`, the continuous − absolute offset, the machine, the source and the observer's CPU), then one line per frame. `BenchObservedVersions` keeps each version's first PTS (its on-glass time) and the unreadable fraction; `BenchObserverAgreement` is C1, and `BenchInputResponses` pairs each input event with the first frame showing another version than the one on screen at the event (C6, and later input-to-photon). An event before any readable frame, or whose change lands after the next event (or after a previous event whose change hadn't landed yet), is unanswered rather than guessed.
- **Gate.** `BenchRegressionGate.regressions(baseline:first:second:)` takes `BenchGateSample`s for one scene and network: the baseline nights (the last 7 count, compared by median) and two consecutive runs. A metric regresses only when both runs pass its threshold: e2e p50 up by more than max(15%, 3 ms), p95 up by more than max(20%, 5 ms), updates/s down by more than 5%, freeze ratio up by more than 2 points (pass it for N3 only), `psnr_y` down by more than 0.5 dB, or an encode or decode error in both runs.
